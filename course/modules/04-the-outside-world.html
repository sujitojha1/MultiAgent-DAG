04

The Outside World

When a skill "asks the AI" or "goes to the web," it leaves this program entirely — and crosses through exactly two guarded gates.

Crossing the boundary

Modules 1–3 were the agent's internal org chart: a cast of skills, wired into a graph that grows and runs itself. But none of that, on its own, knows a single fact about the world. When the Researcher "goes to the web" or "asks the AI," where does that actually go? Out of this program entirely — to services that cost money, have rate limits, and sometimes fail.

🏢
The metaphor: an embassy switchboard

Picture a building full of specialists. No one phones a foreign government directly. They hand every request to one front desk — the Gateway — which knows which interpreter is on duty, keeps a logbook, and redials when a line drops. And when a specialist needs something from the real world, they request it through a fixed set of approved hotlines (tools) — never by reaching out on their own.

So there are exactly two gates out of the system. Meet them both.

🧠
The brain — the Gateway

Every call to an AI model funnels through one front desk that picks a provider, retries, caches, and logs.

🛠️
The hands — tools

A skill can only touch the world through a small, declared menu of tools. No tools on its list? It can think, but it cannot reach.

The Gateway: one front desk for every AI call

Why funnel everything through one place? Because one front desk gives you one place to track cost, one logbook, one retry policy, one cache, and one knob to choose which provider answers. In this repo the Gateway is a separate service — a small FastAPI server running at http://localhost:8108. A skill never names OpenAI or Gemini directly — it talks to its own switchboard, and the switchboard decides.

💡
Aha! One door, one place to fix things

One gateway means one place to see cost, one place to add a missing key, and one place to fix a provider outage — instead of hunting through every skill. That is the whole reason to funnel.

Routing: different jobs, different interpreters

Because every call passes through the Gateway, you can send different skills to different providers — and even pin a skill to a specific one. Here is a real decision from this repo's config — and the honest engineering reason is right there in the comment.

CODE 
github_research:
  prompt: prompts/github_research.md
  provider_pin: gemini     # drive fetch_url tool-loop + JSON on gemini; ollama
                           # returned empty {} after 91s (couldn't tool-call)
  tools_allowed: [fetch_url]
  temperature: 0.2         # structured extraction; keep it deterministic
  max_tokens: 2000
  description: Fetches live data from GitHub trending pages and the GitHub API.
PLAIN ENGLISH

This skill is pinned to the Gemini provider — always route its calls there.

Why? The comment says it plainly: another provider couldn't reliably use tools and stalled for 91 seconds, returning nothing.

It is allowed exactly one tool — fetch_url — and nothing else.

Low temperature keeps its structured extraction steady.

This is what "choosing a model for a job" looks like in practice — a one-line pin, with the reason recorded.

github_research 📌 provider_pin: gemini — the only provider that reliably tool-called for this job.
Gateway 🔌 listening on :8108 — one numbered door every AI call goes through.

Tools: the approved hotlines

The Gateway is the brain; tools are the hands. A skill may only call tools on its menu — the tools_allowed list you saw in Module 2. This agent ships with exactly three.

🔎

web_search

Find pages on the open web (Tavily primary, DuckDuckGo fallback). Hard-capped at 5 results — a built-in guardrail against cost and noise.

📄

fetch_url

Read one page and return it as clean text. Hand it a URL, get back readable markdown.

🧠

search_knowledge

Search what the agent already knows — a vector search over its own saved notes, no internet required.

Each tool is a tiny contract: a name, what it does, and exactly what inputs it accepts. The AI can only ask for tools shaped like this — and only the ones its skill is allowed.

CODE

            "required": ["query"],
        },

PLAIN ENGLISH

A tool named web_search.

A one-line description the AI reads to know when to reach for it — note it even states the 5-result cap.

The input schema: the exact shape of a valid request.

It takes a query string and an optional max_results number...

...but query is the only required field. No query, no call.

That's the whole contract. The AI fills in this shape; the tool does the rest.

Researcher 🌐 web_search   🌐 fetch_url — granted the hands to reach the open web.
Formatter 🚫 no tools — it polishes text the team already produced; it physically cannot browse.
🔒
Aha! Capability is granted, not assumed

A skill with an empty tools_allowed list is thinking-only — it literally cannot touch the internet, no matter what its prompt says. That is a safety feature, not a limitation. Want a skill to gain a new power? Add a tool to its menu. Don't, and it stays blindfolded by design.

When the line is busy

The outside world is not always available. Providers rate-limit you, keys expire, services go down. The Gateway already retries transient blips — but when every provider is unavailable, it surfaces a clear signal instead of pretending. The repo's own troubleshooting table spells it out:

503 Service Unavailable All providers are in cooldown or unconfigured. Fix: add an API key, or wait a minute for cooldowns to clear.

A 503 is not a crash — it is the system honestly reporting that the outside world is, for the moment, out of reach. Which raises the real question of the next module: when a call fails, or worse, when the AI confidently makes something up — what does the agent do about it?

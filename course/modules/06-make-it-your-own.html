Make It Your Own

The engine is finished. Everything you'd want to add is a prompt and a config line — and when the answer needs real math, the agent stops guessing and runs actual code.

Why not just ask the AI to do the math?

Suppose the answer needs real arithmetic — rank 13 repositories by a formula. You could ask the AI to compute it in its head. Don't. Language models are notoriously shaky at arithmetic and will confidently return wrong totals. The fix is better: have the AI write a tiny program, then actually run it and read back the exact result.

🧮
The real task from this repo

Rank trending repos by "velocity" = stars_gained / total_stars × 100. Ask an AI to eyeball that across 13 repos and you'll get plausible-looking nonsense. So the agent hires a one-off contractor instead.

💡
Aha! Bad at arithmetic, good at writing code that does arithmetic

An AI guessing a total is a gamble. An AI writing the program that computes the total is reliable — because a real CPU runs it. Letting it run real code turns a guess into a computation.

The Coder writes a tiny program

The Coder skill's whole job is to emit runnable Python plus a one-line reason. But there's a crucial subtlety. The code runs in a subprocess sandbox that starts with an empty namespace — it cannot see the agent's data. So the Coder must paste the numbers it needs directly into the code as literals.

CODE 
Your Python runs in a separate subprocess sandbox that does NOT see
INPUTS. It starts with an empty namespace. Therefore any number, string,
or list you need from INPUTS must be copied into the source you emit as a
literal — the code cannot reference the upstream output at runtime.
PLAIN ENGLISH

The program runs in a fresh, empty room — none of the agent's data is in it.

So every number, string, or list the program needs...

...must be written straight into the program text as a literal.

The code can't reach back and grab the upstream output while it runs — if it tries, it finds nothing.

🧺
The code must carry its own groceries

The kitchen is bare. If the Coder forgets to pack the numbers into the program itself, the program runs against nothing and produces nothing useful. Inlining the data isn't a quirk — it's the rule.

The automatic hand-off

How does the written code actually get run? Not by the Planner — by config. One line makes Coder and Sandbox inseparable: whenever a Coder finishes, the orchestrator automatically adds a internal successor to run its code next.

CODE 
coder:
  prompt: prompts/coder.md
  internal_successors: [sandbox_executor]
  temperature: 0.2
  max_tokens: 1500
  description: Emits Python code; the orchestrator hands it to sandbox_executor next.
PLAIN ENGLISH

The Coder skill, defined like any other (Module 2).

It points at its instructions file.

internal_successors: [sandbox_executor] means "whenever a Coder finishes, automatically wire a SandboxExecutor right after it."

The usual dials — steady temperature, a token cap.

The Planner never has to ask for the sandbox. The pairing is baked into the config.

And here is the orchestrator honouring that config — the generic mechanism, with no skill-specific code:

CODE 
        for child_skill in src_def.internal_successors:
            nid = self.add_node(child_skill, inputs=[src_nid])
            added.append(nid)
PLAIN ENGLISH

After any node finishes, look up its internal_successors from the config...

...and add each one as a new box, fed by the node that just finished.

That's the whole hand-off — generic, no if skill == "coder" anywhere.

🔗
Aha! Some edges are wired by config, not planned

Back in Module 3 the Planner grew the graph at runtime. Here is the other kind of track-laying: static edges decided ahead of time by the YAML. Coder→Sandbox is never planned — it's guaranteed by one config line.

The rented workshop (and what it does NOT protect)

The code runs in a sandbox. It is tempting to call that a security jail. The sandbox itself, refreshingly, tells you it is not:

CODE 
What it is NOT. This is not OS-level isolation. There is no chroot, no
container, no syscall filter, no FS allowlist beyond cwd. A malicious
script can read /etc and call out to the network. The sandbox is a
USABILITY boundary — it keeps a runaway loop or noisy print from
poisoning the orchestrator's stdout — not a SECURITY boundary.
PLAIN ENGLISH

Honest self-documentation: this is not isolation.

No container, no locked-down filesystem beyond the working folder.

A genuinely malicious script could still read files or reach the network.

What it does do: stop a runaway loop or a giant stdout flood from poisoning the run.

It's a usability boundary, not a security one. Know the difference.

⏱ timeout 30 seconds — a runaway script is killed, not left to spin forever.
📦 output cap 1 MB — a noisy program can't flood the orchestrator's output.
🔒 env scrubbed Most environment variables removed; only PATH / HOME / LANG kept.

And the payoff: an exact answer

On the real velocity task, the emitted code ran in about 0.1 seconds and produced an exact ranking — top repo at 97.37% velocity. No guesswork, no hallucinated totals: a real computation with a real number.

Add a whole skill with zero Python

Here is the finale's thesis, and the repo proves it. The github_research skill — a real, working capability — shipped with no Python changes at all. Look at the actual diff stat from the commit that introduced it:

CODE 
 code/agent_config.yaml          |  18 +++   ← skill entry + provider_pin + tools_allowed
 code/prompts/github_research.md |  28 ++++  ← full system prompt (new file)
 gateway/agent_routing.yaml      |   1 +     ← routing hint only
PLAIN ENGLISH

A config entry — the skill's name, its provider pin, its allowed tools.

A new prompt file — the skill's whole "brain," in plain English.

A one-line routing hint so the Gateway (Module 4) knows where to send it.

Three small text edits. Not one line of program logic changed.

That ties back to Module 2 (a skill is two files) and Module 4 (provider routing). The recipe for a new capability is just three steps:

1

Write the prompt

A Markdown file describing who the skill is and its one job — its entire "intelligence."

2

Add the YAML entry

Name it, point at the prompt, set its dials and any tools. The registry picks it up automatically.

3

Routing hint (optional)

One line if it needs a specific provider. Otherwise the Gateway just chooses.

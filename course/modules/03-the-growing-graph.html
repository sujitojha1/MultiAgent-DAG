The Graph That Grows Itself

How the agent builds its own plan while it runs — and runs the independent parts side by side.

Who wrote the plan?

Back in Module 1, a friendly "hello" used 2 specialists and a research question used 4. Nobody hand-wrote those two different pipelines. The agent grows its own plan while it runs.

🏁
The metaphor: a relay race where the track builds itself

Each runner finishes their leg and lays down the next stretch of track for whoever comes next. Some legs split into several lanes run side by side. The finish line is not drawn in advance — it appears as the race unfolds.

DAG: Directed Acyclic Graph

The arrows have a direction (directed) and they never circle back on themselves (acyclic). Boxes and one-way arrows that never form a loop — that is a DAG.

A finished skill lays new track

When a box finishes, the orchestrator splices in the successors that box asked for: it adds the new boxes, then wires their arrows. This is the heart of a graph that grows at runtime.

CODE 
    def add_node(self, skill: str, inputs: list[str], metadata: dict | None = None) -> str:
        self._counter += 1
        nid = f"n:{self._counter}"
        self.g.add_node(nid, skill=skill, inputs=list(inputs),
                        metadata=dict(metadata or {}), status="pending")
        for inp in inputs:
            if inp.startswith("n:") and inp in self.g.nodes:
                self.g.add_edge(inp, nid)
        return nid

Aha! The plan is data, not code

The agent edits its own to-do graph while running. That is why two different questions produce two different pipelines from the exact same program — nobody wrote either pipeline by hand.

Parallel lanes — run together, wait only where you must

How does the agent know what can run together? Any box whose feeding boxes are all done is "ready," and all ready boxes fire at once. First, finding the ready ones.

CODE 
    def ready_nodes(self) -> list[str]:
        # A predecessor counts as "satisfied" when it is either complete or
        # skipped (the latter is how a Critic-fail removes a child from the
        # critical path without blocking unrelated branches downstream).
        out = []
        for nid, d in self.g.nodes(data=True):
            if d["status"] != "pending":
                continue
            preds = list(self.g.predecessors(nid))
            if all(self.g.nodes[p]["status"] in ("complete", "skipped") for p in preds):
                out.append(nid)
        return out
PLAIN ENGLISH

Find every box that is allowed to run right now.

A box that feeds into another (its predecessor) counts as done if it either completed or was skipped.

Skipping is how a failed check quietly drops one branch without freezing the unrelated ones.

Why no loops — and a hard safety rail

A DAG is acyclic on purpose. A plan that could point back at itself could keep handing the baton in a circle and run forever. There is also a hard cap so a misbehaving Planner cannot grow the graph endlessly.

MAX_NODES = 60 Safety rail: the plan can never grow past 60 boxes, no matter what the Planner asks for.
acyclic No cycles allowed — follow the arrows and you can never loop back to where you started. The plan always ends.
🔁
A loop is a trap

If box A waited on B and B waited on A, neither could ever become "ready" — both would wait forever. Forbidding cycles is what guarantees the relay always reaches a finish line.

When the AI Is Wrong

AI makes things up — confidently. So the agent hires a professional skeptic, gives it veto power, and sorts every failure into "retry," "fix it," or "rethink."

So how does this agent avoid shipping garbage? It does not trust any skill's word for it. It hires a Critic — a professional skeptic — and gives it the power to say no.

Meet the Critic

The Critic is a skill like any other (Module 2: two files, a few dials). But it is unusual in one way — its output is not a transformed document. It is just a verdict: pass or fail, plus a sentence of why. It is a gate, not a step that changes anything.

CODE 
Procedure:
  1. Read the UPSTREAM_OUTPUT.
  2. Check it against the INPUTS that produced it.
  3. Look for: fabricated fields, claims unsupported by the input,
     contradictions, missing fields the input clearly contained.
  4. Emit pass or fail.

Output schema (JSON, no prose, no markdown fences):

  {
    "verdict": "pass" | "fail",
    "rationale": "<one or two short sentences>"
  }
PLAIN ENGLISH

Read the work that was just produced...

...and read the source material it was built from.

Hunt for the four classic sins: invented facts, unsupported claims, contradictions, and dropped fields the input clearly had.

Decide: pass or fail.

Return a tiny object — the verdict, plus a one- or two-sentence rationale.

That is the entire skeptic: read, compare, judge, explain.

Critic 🎯 temperature 0.0 — we want the same judgment every time on the same input (callback to Module 2's dials).
🚦
It carries no data of its own

The Critic transforms nothing. It produces no report, no summary, no answer — only a yes-or-no with a reason. Its single power is to say no, and as you will see, that is enough to stop garbage from shipping.

A FAIL rewires the graph

Here the growing-graph idea from Module 3 pays off. A failing verdict does not crash the run — it edits the plan. The rejected work's child is marked skipped, and a brand-new Planner box is spliced in to try again — handed the Critic's reason so it can plan a smarter second attempt.

The one-rework rule

Without a limit, a stubborn failure could re-plan forever. So every branch gets exactly one rescue. A second failure logs a loud warning and lets the run finish with a noted gap — graceful degradation instead of an infinite loop.

Not all failures are equal

The Critic catches answers that are wrong but well-formed. A separate classifier handles outright errors — and it sorts every one into a bucket with a clear action. The decision table reads almost like prose:

CODE 
    Decision table (all coverage):
      reason=transient                          → skip (gateway already retried)
      reason=validation_error                   → skip (prompt bug, not runtime)
      reason=upstream_failure, failed=planner   → skip (would loop on Planner errors)
      reason=upstream_failure, failed=other     → replan
PLAIN ENGLISH

A transient blip (like a 503)? Skip it — the gateway already retried, so re-planning would waste time.

A validation error (malformed output)? Skip it — that's a prompt bug; re-running the same prompt won't fix it.

A real content failure in a normal skill? Re-plan — this is the one worth a smarter second try.

But never re-plan a failed Planner — that would just loop on Planner errors.

💡
Aha! Three debugging questions for any flaky AI step

Is it a blip (just retry), a bad instruction (fix the prompt — don't retry), or a real dead-end (rethink the approach)? This agent encodes exactly that as skip / skip / re-plan. Learn to ask these three and you escape "AI bug loops" instead of mashing retry forever.

def main() -> None:
    args = sys.argv[1:]
    resume_sid: str | None = None
    if args and args[0] == "--resume":
        resume_sid = args[1] if len(args) > 1 else None
        query = " ".join(args[2:])
    else:
        query = " ".join(args) or "Say hello in one short sentence."
    asyncio.run(Executor().run(query, session_id=resume_sid, resume=bool(resume_sid)))

One engine, many actors

If a skill is just two files, what reads them? One small loader — the registry. And it does not have a special case per skill.

class SkillRegistry:
    def __init__(self):
        cfg = yaml.safe_load(AGENT_CONFIG_PATH.read_text())
        self._skills: dict[str, Skill] = {n: Skill(n, c) for n, c in cfg.items()}

    def get(self, name: str) -> Skill:
        if name not in self._skills:
            raise KeyError(f"unknown skill: {name}")
        return self._skills[name]

When it starts up, it reads the whole config file.

If you searched this codebase for if skill == 'researcher' you would not find it. The orchestrator treats every member identically. Adding a skill to the YAML makes it loadable; removing it makes it unknown. That's it.

Prompt vs. engine

This is the single most empowering idea for steering AI tools. There are two different things, and people constantly confuse them:

✍️
The prompt

The English instructions in a .md file. Editable by anyone. This is where most of the "smartness" lives.

⚙️
The engine

The unchanging Python that loads instructions and delivers them. It doesn't know or care which skill it's running.

💡
Aha! Prompt vs. engine

The prompt is the English instructions; the engine is the unchanging code that delivers them. Most of what feels like "the AI being smart" actually lives in editable prompt files you can open and change yourself.

The Graph That Grows Itself

How the agent builds its own plan while it runs — and runs the independent parts side by side.

Who wrote the plan?

Back in Module 1, a friendly "hello" used 2 specialists and a research question used 4. Nobody hand-wrote those two different pipelines. The agent grows its own plan while it runs.

🏁
The metaphor: a relay race where the track builds itself

Each runner finishes their leg and lays down the next stretch of track for whoever comes next. Some legs split into several lanes run side by side. The finish line is not drawn in advance — it appears as the race unfolds.

DAG: Directed Acyclic Graph

The arrows have a direction (directed) and they never circle back on themselves (acyclic). Boxes and one-way arrows that never form a loop — that is a DAG.

A finished skill lays new track

When a box finishes, the orchestrator splices in the successors that box asked for: it adds the new boxes, then wires their arrows. This is the heart of a graph that grows at runtime.

CODE 
    def add_node(self, skill: str, inputs: list[str], metadata: dict | None = None) -> str:
        self._counter += 1
        nid = f"n:{self._counter}"
        self.g.add_node(nid, skill=skill, inputs=list(inputs),
                        metadata=dict(metadata or {}), status="pending")
        for inp in inputs:
            if inp.startswith("n:") and inp in self.g.nodes:
                self.g.add_edge(inp, nid)
        return nid
PLAIN ENGLISH

A request to add one new box: which skill it runs, and what it reads.

Give it the next number in line...

...so it gets a unique name like n:5.

Record the box: its skill, its inputs, any notes, and mark it pending — not started.

Now look at each thing this box reads...

...and if it is actually another box (a name like n:...)...

...draw an arrow from that box to this one.

Hand back the new box name. Inputs literally became the dependency arrows.

Aha! The plan is data, not code

The agent edits its own to-do graph while running. That is why two different questions produce two different pipelines from the exact same program — nobody wrote either pipeline by hand.

Parallel lanes — run together, wait only where you must

How does the agent know what can run together? Any box whose feeding boxes are all done is "ready," and all ready boxes fire at once. First, finding the ready ones.

CODE 
    def ready_nodes(self) -> list[str]:
        # A predecessor counts as "satisfied" when it is either complete or
        # skipped (the latter is how a Critic-fail removes a child from the
        # critical path without blocking unrelated branches downstream).
        out = []
        for nid, d in self.g.nodes(data=True):
            if d["status"] != "pending":
                continue
            preds = list(self.g.predecessors(nid))
            if all(self.g.nodes[p]["status"] in ("complete", "skipped") for p in preds):
                out.append(nid)
        return out
PLAIN ENGLISH

Find every box that is allowed to run right now.

A box that feeds into another (its predecessor) counts as done if it either completed or was skipped.

Skipping is how a failed check quietly drops one branch without freezing the unrelated ones.

Start an empty ready-list.

Walk through every box...

...ignore any box that is not still pending...

...look at every box with an arrow into it...

...and if every one of them has finished or been skipped...

...this box is ready — add it.

Return the whole ready list. These can all go now.

Why no loops — and a hard safety rail

A DAG is acyclic on purpose. A plan that could point back at itself could keep handing the baton in a circle and run forever. There is also a hard cap so a misbehaving Planner cannot grow the graph endlessly.

MAX_NODES = 60 Safety rail: the plan can never grow past 60 boxes, no matter what the Planner asks for.
acyclic No cycles allowed — follow the arrows and you can never loop back to where you started. The plan always ends.
🔁
A loop is a trap

If box A waited on B and B waited on A, neither could ever become "ready" — both would wait forever. Forbidding cycles is what guarantees the relay always reaches a finish line.

04

The Outside World

When a skill "asks the AI" or "goes to the web," it leaves this program entirely — and crosses through exactly two guarded gates.

Crossing the boundary

Modules 1–3 were the agent's internal org chart: a cast of skills, wired into a graph that grows and runs itself. But none of that, on its own, knows a single fact about the world. When the Researcher "goes to the web" or "asks the AI," where does that actually go? Out of this program entirely — to services that cost money, have rate limits, and sometimes fail.

🏢
The metaphor: an embassy switchboard

Picture a building full of specialists. No one phones a foreign government directly. They hand every request to one front desk — the Gateway — which knows which interpreter is on duty, keeps a logbook, and redials when a line drops. And when a specialist needs something from the real world, they request it through a fixed set of approved hotlines (tools) — never by reaching out on their own.

So there are exactly two gates out of the system. Meet them both.

🧠
The brain — the Gateway

Every call to an AI model funnels through one front desk that picks a provider, retries, caches, and logs.

🛠️
The hands — tools

A skill can only touch the world through a small, declared menu of tools. No tools on its list? It can think, but it cannot reach.

The Gateway: one front desk for every AI call

Why funnel everything through one place? Because one front desk gives you one place to track cost, one logbook, one retry policy, one cache, and one knob to choose which provider answers. In this repo the Gateway is a separate service — a small FastAPI server running at http://localhost:8108. A skill never names OpenAI or Gemini directly — it talks to its own switchboard, and the switchboard decides.

Tools: the approved hotlines

The Gateway is the brain; tools are the hands. A skill may only call tools on its menu — the tools_allowed list you saw in Module 2. This agent ships with exactly three.

🔎

web_search

Find pages on the open web (Tavily primary, DuckDuckGo fallback). Hard-capped at 5 results — a built-in guardrail against cost and noise.

📄

fetch_url

Read one page and return it as clean text. Hand it a URL, get back readable markdown.

🧠

search_knowledge

Search what the agent already knows — a vector search over its own saved notes, no internet required.

Each tool is a tiny contract: a name, what it does, and exactly what inputs it accepts. The AI can only ask for tools shaped like this — and only the ones its skill is allowed.

Aha! Capability is granted, not assumed

A skill with an empty tools_allowed list is thinking-only — it literally cannot touch the internet, no matter what its prompt says. That is a safety feature, not a limitation. Want a skill to gain a new power? Add a tool to its menu. Don't, and it stays blindfolded by design.

When the line is busy

The outside world is not always available. Providers rate-limit you, keys expire, services go down. The Gateway already retries transient blips — but when every provider is unavailable, it surfaces a clear signal instead of pretending. The repo's own troubleshooting table spells it out:

503 Service Unavailable All providers are in cooldown or unconfigured. Fix: add an API key, or wait a minute for cooldowns to clear.

A 503 is not a crash — it is the system honestly reporting that the outside world is, for the moment, out of reach. Which raises the real question of the next module: when a call fails, or worse, when the AI confidently makes something up — what does the agent do about it?

05

When the AI Is Wrong

AI makes things up — confidently. So the agent hires a professional skeptic, gives it veto power, and sorts every failure into "retry," "fix it," or "rethink."

AI lies confidently

Large language models hallucinate: they invent dates, fabricate sources, and quietly drop half of what you asked for. And it all sounds equally confident. Here is a real miss from this very repo — a run that asked for trending Python and Rust repositories:

🐛
A real silent miss

The distilled answer "only includes Python repositories, but the user query also asked for Rust repositories." Nothing crashed. No error was thrown. The answer just quietly left out half the request — exactly the kind of mistake a confident AI makes and a careless pipeline ships.

So how does this agent avoid shipping garbage? It does not trust any skill's word for it. It hires a Critic — a professional skeptic — and gives it the power to say no.

Meet the Critic

The Critic is a skill like any other (Module 2: two files, a few dials). But it is unusual in one way — its output is not a transformed document. It is just a verdict: pass or fail, plus a sentence of why. It is a gate, not a step that changes anything.

CODE 
Procedure:
  1. Read the UPSTREAM_OUTPUT.
  2. Check it against the INPUTS that produced it.
  3. Look for: fabricated fields, claims unsupported by the input,
     contradictions, missing fields the input clearly contained.
  4. Emit pass or fail.

Output schema (JSON, no prose, no markdown fences):

  {
    "verdict": "pass" | "fail",
    "rationale": "<one or two short sentences>"
  }
PLAIN ENGLISH

Read the work that was just produced...

...and read the source material it was built from.

Hunt for the four classic sins: invented facts, unsupported claims, contradictions, and dropped fields the input clearly had.

Decide: pass or fail.

Return a tiny object — the verdict, plus a one- or two-sentence rationale.

That is the entire skeptic: read, compare, judge, explain.

Critic 🎯 temperature 0.0 — we want the same judgment every time on the same input (callback to Module 2's dials).
🚦
It carries no data of its own

The Critic transforms nothing. It produces no report, no summary, no answer — only a yes-or-no with a reason. Its single power is to say no, and as you will see, that is enough to stop garbage from shipping.

A FAIL rewires the graph

Here the growing-graph idea from Module 3 pays off. A failing verdict does not crash the run — it edits the plan. The rejected work's child is marked skipped, and a brand-new Planner box is spliced in to try again — handed the Critic's reason so it can plan a smarter second attempt.

The one-rework rule

Without a limit, a stubborn failure could re-plan forever. So every branch gets exactly one rescue. A second failure logs a loud warning and lets the run finish with a noted gap — graceful degradation instead of an infinite loop.

CODE

              f"CAP HIT — branch skipped, final will reflect missing data")

If we reach here, this branch already used its one do-over — and failed again.

Print a loud warning — and be honest that the final answer will reflect the missing data.

Then let the run finish. No third attempt, no infinite loop.

recovery cap = 1 Per branch. One rescue, then ship with a noted gap rather than loop.

Not all failures are equal

The Critic catches answers that are wrong but well-formed. A separate classifier handles outright errors — and it sorts every one into a bucket with a clear action. The decision table reads almost like prose:

CODE 
    Decision table (all coverage):
      reason=transient                          → skip (gateway already retried)
      reason=validation_error                   → skip (prompt bug, not runtime)
      reason=upstream_failure, failed=planner   → skip (would loop on Planner errors)
      reason=upstream_failure, failed=other     → replan
PLAIN ENGLISH

A transient blip (like a 503)? Skip it — the gateway already retried, so re-planning would waste time.

A validation error (malformed output)? Skip it — that's a prompt bug; re-running the same prompt won't fix it.

A real content failure in a normal skill? Re-plan — this is the one worth a smarter second try.

But never re-plan a failed Planner — that would just loop on Planner errors.

💡
Aha! Three debugging questions for any flaky AI step

Is it a blip (just retry), a bad instruction (fix the prompt — don't retry), or a real dead-end (rethink the approach)? This agent encodes exactly that as skip / skip / re-plan. Learn to ask these three and you escape "AI bug loops" instead of mashing retry forever.

Why not just ask the AI to do the math?

Aha! Bad at arithmetic, good at writing code that does arithmetic

An AI guessing a total is a gamble. An AI writing the program that computes the total is reliable — because a real CPU runs it. Letting it run real code turns a guess into a computation.

The Coder writes a tiny program

The Coder skill's whole job is to emit runnable Python plus a one-line reason. But there's a crucial subtlety. The code runs in a subprocess sandbox that starts with an empty namespace — it cannot see the agent's data. So the Coder must paste the numbers it needs directly into the code as literals.

CODE 
Your Python runs in a separate subprocess sandbox that does NOT see
INPUTS. It starts with an empty namespace. Therefore any number, string,
or list you need from INPUTS must be copied into the source you emit as a
literal — the code cannot reference the upstream output at runtime.
PLAIN ENGLISH

The program runs in a fresh, empty room — none of the agent's data is in it.

So every number, string, or list the program needs...

...must be written straight into the program text as a literal.

The code can't reach back and grab the upstream output while it runs — if it tries, it finds nothing.

🧺
The code must carry its own groceries

The kitchen is bare. If the Coder forgets to pack the numbers into the program itself, the program runs against nothing and produces nothing useful. Inlining the data isn't a quirk — it's the rule.

The rented workshop (and what it does NOT protect)

The code runs in a sandbox. It is tempting to call that a security jail. The sandbox itself, refreshingly, tells you it is not:

CODE 
What it is NOT. This is not OS-level isolation. There is no chroot, no
container, no syscall filter, no FS allowlist beyond cwd. A malicious
script can read /etc and call out to the network. The sandbox is a
USABILITY boundary — it keeps a runaway loop or noisy print from
poisoning the orchestrator's stdout — not a SECURITY boundary.
PLAIN ENGLISH

Honest self-documentation: this is not isolation.

No container, no locked-down filesystem beyond the working folder.

A genuinely malicious script could still read files or reach the network.

What it does do: stop a runaway loop or a giant stdout flood from poisoning the run.

It's a usability boundary, not a security one. Know the difference.

⏱ timeout 30 seconds — a runaway script is killed, not left to spin forever.
📦 output cap 1 MB — a noisy program can't flood the orchestrator's output.
🔒 env scrubbed Most environment variables removed; only PATH / HOME / LANG kept.

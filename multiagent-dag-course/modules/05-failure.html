When Things Break

A call times out. A specialist returns garbage. Someone yanks the power cord mid-run. A real agent has to survive all three — and this one does.

The metaphor: GPS on a road trip

You're driving with GPS. Things go wrong constantly — and a good GPS responds differently depending on what kind of wrong it is. It doesn't recalculate the entire route every time a single light turns red.

🗺️
The core skill of this module

Not all failures deserve the same response. Knowing which failures to retry, ignore, or re-plan around is the difference between an agent that recovers and one that spins forever.

Three kinds of "wrong"

When a node fails, the system first classifies the failure into one of three buckets:

🚧

Transient → skip

A timeout or "all lines busy." The toll booth was briefly shut. The gateway already retried — no point re-planning.

📝

Validation error → skip

A specialist produced malformed output. That's a typo in the address — re-planning won't fix it. Fix the prompt.

🛣️

Upstream failure → re-plan

The road is genuinely closed. This is when it's worth sending the Planner back to find another route.

The classifier, in its own words

CODE · recovery.py 
if "malformed" in e or "validationerror" in e:
    return "validation_error"
transient_markers = ("503", "502", "timeout", ...)
if any(m in e for m in transient_markers):
    return "transient"
return "upstream_failure"
PLAIN ENGLISH

If the error text mentions a structure problem…

…call it a validation error (a prompt bug).

Keep a list of "temporary glitch" signals.

If the error matches any of them…

…call it transient (it'll probably pass).

Anything else is a real, structural failure worth re-planning.

🔁
The infinite-loop guard

One special rule: if the Planner itself fails, never re-plan. Asking a broken GPS to recalculate forever is how agents get stuck. That single guard is what keeps the whole system from looping.

The fact-checker's veto

Remember the Critic from Module 2? When a specialist is marked "needs checking," a Critic is slotted in front of the next step. If the Critic says fail, a careful sequence kicks off:

1

Critic returns fail + a reason

→
2

The waiting child is marked skipped

→
3

A fresh Planner is spliced in with the failure reason

🎯
…but only once per branch (the cap)

That re-plan is allowed exactly one time per branch. If the redo also fails the Critic, the system stops trying and loudly warns you that the final answer is missing data — instead of silently looping or silently lying. Honesty over pretending, again.

Surviving a power-cord yank

Here's the scary one. What if the process is killed mid-run — laptop dies, someone hits Ctrl-C hard? The agent keeps an autosave. Every change to the board is written to disk safely:

CODE · persistence.py 
tmp = path.with_suffix(path.suffix + ".tmp")
tmp.write_text(data)
os.replace(tmp, path)
PLAIN ENGLISH

Write the new save to a temporary file first.

Fill it completely, off to the side.

Only then swap it into place in one instant move. If the plug is pulled mid-write, the old save is still intact. This is an atomic write.

Picking up where it left off

When you re-run with --resume, the agent loads the saved board and does one clever thing: any node that was mid-flight when the plug was pulled gets reset to "not started," so it runs again cleanly. Finished nodes are left untouched.

CODE · flow.py 
for _, d in graph.g.nodes(data=True):
    if d["status"] == "running":
        d["status"] = "pending"
PLAIN ENGLISH

Look at every node on the restored board.

If it was caught mid-run when we died…

…mark it "not started" so it runs fresh. Already-finished work is never redone — no wasted calls, no duplicates.

💾
Why you'd want this in your own apps

Long AI runs cost real money. Restarting from zero after a crash means paying twice. "Save progress safely, resume from the boundary" is a pattern worth asking your AI assistant to build into anything that runs for minutes.

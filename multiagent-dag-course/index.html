How a Multi-Agent DAG Agent Works
01

What This Thing Actually Does

You type a question. A team of AI specialists assembles itself, works in parallel, and hands you back one answer. Let's watch it happen.

Start with something you'd actually type

Imagine you open a terminal and run this:

CODE 
uv run python flow.py "Compare the populations of London, Paris, and Berlin"
PLAIN ENGLISH

You ask one plain-English question.

Behind the scenes, that single line kicks off a whole team of AI workers — not one big AI doing everything.

This project is an AI agent. Its one job: take a messy human request and figure out how to answer it by orchestrating a team of small, focused specialists.

The metaphor: a newsroom on deadline

The cleanest way to picture this system is a newsroom. You're the reader who wants a story. Nobody writes the whole thing alone:

The Formatter writes the answer that lands in your terminal.

Instead of one giant AI trying to do everything, the work is split into small specialists. Each one is good at exactly one thing. Engineers call this separation of concerns — and it's the single most important pattern in this whole codebase.

02

The Cast of Characters

Meet the specialists. The twist: not one of them is written in Python. Each is just a text file and a few lines of config.

A skill is an actor with a playbill

Think of a theater playbill. Every actor has two things: a script telling them what to say, and a casting sheet with their role and rules. A skill here works the exact same way:

📜

The script

A plain Markdown file in prompts/ — the instructions handed to the AI. This is the actor's lines.

🗂️

The casting sheet

One entry in agent_config.yaml — which tools it may use, how creative it's allowed to be, what it does.

🤯
The surprising part

There is no Python class per skill. No class Researcher: anywhere. A skill is 100% a prompt file + a config entry. You'll see in Module 6 why this is the whole point of the design.

The main cast

Six specialists do almost all the work. Each is good at exactly one thing:

📋

Planner

Reads your question and writes the list of who should run. The editor of the newsroom.

🔎

Researcher

Searches the web and reads pages. The only one allowed to leave the building.

🗄️

Retriever

Searches the agent's own memory — documents it already filed away. The in-house archivist.

🧪

Distiller

Pulls clean, structured facts out of messy text. (And it always gets fact-checked — Module 5.)

⚖️

Critic

Approves or rejects another specialist's work. Says only "pass" or "fail" with a reason.

✍️

Formatter

Writes the final answer you read. Always the last node — engineers call this a terminal.

A casting sheet, line by line

Here is the entire definition of the Researcher. Notice there's no logic here — just a description of what kind of worker it is:

CODE · agent_config.yaml 
researcher:
  prompt: prompts/researcher.md
  tools_allowed: [web_search, fetch_url]
  temperature: 0.7
  max_tokens: 2500
  description: Performs multi-step web research.
PLAIN ENGLISH

A specialist named "researcher".

Its instructions live in this Markdown file.

It's allowed to use two tools: web search and fetching a page. Most specialists get none.

Temperature 0.7 = fairly exploratory, good for open research.

It may write up to 2500 tokens of output.

A one-line human summary. That's the whole definition.

🎚️
A knob worth knowing

The Critic and Distiller run at temperature: 0 (be exact, no surprises). The Researcher runs hot at 0.7 (explore). Tuning a specialist's behavior is a one-line edit to this file — no code change. This is exactly the kind of dial you can tell an AI assistant to adjust.

How the config becomes a working team

On startup, the system reads that whole config file and turns every entry into a skill object it can run. One loop, no special cases:

The "registry" is just the cast list, loaded into memory.

When it's built…

…read the whole config file (that's what YAML is).

…and for every single entry, make one skill object. Add a new entry to the file and it just shows up. No code edit needed.

03

How the Graph Grows & Runs at Once

The team isn't a fixed assembly line. It draws new workers onto the board as it goes — and runs everyone it can, all at the same time.

The metaphor: a construction schedule

Picture building a house. Some jobs must wait — you can't roof before the walls are up. But plumbing and electrical can happen at the same time. A site manager doesn't do them one-by-one; they start everything whose prerequisites are met.

⛓️
An arrow means "wait for this"

Roof waits for walls. In code, an edge A→B means B can't start until A finishes.

⚡
No arrow between them? Do both now.

Plumbing and wiring run together. Three Researchers with no dependency on each other run concurrently.

The whole engine, in one sentence

The orchestrator repeats a tiny loop until there's nothing left to do:

1

Find every node whose prerequisites are done

→
2

Run them all at once

→
3

Let finished nodes add new nodes

→
4

Repeat

🔁
This is "the graph is the agent loop"

There's no giant scripted pipeline. Just: find-ready, run-ready, grow, repeat. The graph's shape emerges as work completes.

"Find every ready node" — the actual code

CODE · flow.py 
preds = list(self.g.predecessors(nid))
if all(self.g.nodes[p]["status"] in ("complete", "skipped")
       for p in preds):
    out.append(nid)
PLAIN ENGLISH

Look at everyone this node is waiting on (its prerequisites).

If all of them are either finished…

…or skipped (a dead branch still unblocks the path)…

…then this node is ready — add it to the "run now" list.

🟡
"Skipped counts as done"

A node that got cancelled still unblocks whatever waited on it. That little detail keeps one dead branch from freezing the whole board. You'll see why it matters in Module 5.

"Run them all at once" — one magic word

CODE · flow.py 
outcomes = await asyncio.gather(
    *[self._run_one(nid, ...) for nid in ready]
)
PLAIN ENGLISH

Kick off every ready node at the same moment…

…using asyncio.gather, which launches them together and waits for all to come back.

This line is why 3 cities take as long as the slowest one, not all three added up.

⏱️
Wall-clock math worth memorizing

3 Researchers taking 30s, 28s, 26s finish in ~30s (the slowest), not 84s (the sum). If you ever see fan-out work taking the sum of its parts, something broke the parallelism — that's a real debugging signal.

How the board grows new notes

After any node succeeds, the orchestrator runs extend_from, which can add new nodes three different ways:

1
The node asked for them

A specialist can return "successors" — new nodes it wants run next. The Planner uses this to create the whole initial team.

2
The config wired them in automatically

Some skills always get a follow-up. The Coder is always followed by a code-runner — the config says so, no one has to ask. (Module 6.)

3
A fact-checker got slotted in

If a skill is marked "needs checking," the system quietly inserts a Critic in front of whatever comes next. (Module 5.)

🧩
Why this is powerful — and where bugs hide

Because the graph builds itself, a node that "should have run" might simply never have been added. When debugging, don't just ask "did the node fail?" — ask "did the node ever get created?"

What a node actually "sees"

A node doesn't get the whole history. It only receives the outputs of its direct predecessors, bundled as JSON inputs. The Formatter sees three research results; it never sees how they were found.

💸
Why narrow inputs = cheaper & sharper

Feeding each specialist only what it needs (not the entire transcript) keeps the prompts small. Smaller prompts = fewer tokens = lower cost and less for the AI to get confused by. This is a deliberate design choice you can copy in your own projects.

04

The Outside World: the Gateway

Every specialist needs an AI brain to think with. None of them talk to an AI directly — they all go through one front desk that decides who handles the call.

The metaphor: a switchboard operator

Imagine a big company with one phone number. A switchboard operator answers every call, sizes it up in a second, and routes it to the right department — billing, support, sales. The caller never dials a department directly.

The Gateway is that operator. Every specialist's request for AI thinking goes through it first.

☎️
One number for everyone

Researcher, Critic, Formatter — all call the same front desk, never an AI vendor directly.

🔀
The operator routes the call

It picks which AI provider (Gemini, Groq, a local model…) should handle this request.

A specialist phoning the front desk

From the specialist's side, calling the AI is almost boringly simple — it just hands its written prompt to the gateway and says who it is:

CODE · skills.py 
reply = await asyncio.to_thread(
    LLM().chat,
    prompt=rendered,
    agent=skill.name,
    temperature=skill.temperature,
)
PLAIN ENGLISH

Make the call (and don't freeze everyone else while we wait).

Dial the gateway's "chat" line.

Here's the question, written out.

"I'm the researcher" — the gateway uses this to bill and route per specialist.

"And here's how creative I'm allowed to be."

🔌
Why route everything through one door?

The agent never hard-codes "use Gemini." Swap providers, add a new one, or handle an outage — all of that lives in the gateway. The specialists don't know or care which AI answered.

How the operator sizes up a call

The gateway has a tiny, cheap AI — a router — that labels each request as one of three sizes, then sends it to a fitting model:

🐣

TINY

Under ~1,000 tokens. "What's the capital of France?" → a small fast model. No need to wake the big one.

🐘

LARGE

1,000–8,000 tokens. A dense research digest → a stronger model that can hold it all.

🛑

HUGE

Over 8,000 tokens. The gateway refuses with a clear error rather than pretend it can do a bad job.

The wall — the cleverest idea in the gateway

Here's the part worth slowing down for. The router decides where a call goes — but it is never shown what the call actually says. It sees only two things:

token_count Roughly how big the request is — a number, nothing else
sample The first 400 + last 400 characters — a peek at the shape, not the content

It never sees the system prompt, the tools, the conversation history, or the answer. By construction, it can't leak any of that into its routing decision.

🧱
Separation of concerns, enforced by code

This is the same principle from Module 1, but stricter: the wall isn't a polite agreement — the router is physically handed only a size and a snippet. You can read the 30 lines and verify it. Good architecture makes the wrong thing impossible, not just discouraged.

When all the lines are busy

These are free AI providers with strict rate limits. The gateway keeps a ring of providers and fails over from one to the next. But if every provider is maxed out, it returns one specific signal:

503 "All workers busy or in cooldown." Not a bug in your code — the free tiers are saturated. Add a key or wait a minute.
fallback_used: true The router itself was too busy, so the gateway used a simple size rule instead. Totally normal — the call still went through.
🩺
This is "honest" failure design

The gateway never silently pretends. A 503 means "I genuinely couldn't, here's why." Building systems that are honest about how they fail is what separates a toy from production software.

05

When Things Break

A call times out. A specialist returns garbage. Someone yanks the power cord mid-run. A real agent has to survive all three — and this one does.

The metaphor: GPS on a road trip

You're driving with GPS. Things go wrong constantly — and a good GPS responds differently depending on what kind of wrong it is. It doesn't recalculate the entire route every time a single light turns red.

🗺️
The core skill of this module

Not all failures deserve the same response. Knowing which failures to retry, ignore, or re-plan around is the difference between an agent that recovers and one that spins forever.

Three kinds of "wrong"

When a node fails, the system first classifies the failure into one of three buckets:

🚧

Transient → skip

A timeout or "all lines busy." The toll booth was briefly shut. The gateway already retried — no point re-planning.

📝

Validation error → skip

A specialist produced malformed output. That's a typo in the address — re-planning won't fix it. Fix the prompt.

🛣️

Upstream failure → re-plan

The road is genuinely closed. This is when it's worth sending the Planner back to find another route.

The classifier, in its own words

CODE · recovery.py 
if "malformed" in e or "validationerror" in e:
    return "validation_error"
transient_markers = ("503", "502", "timeout", ...)
if any(m in e for m in transient_markers):
    return "transient"
return "upstream_failure"
PLAIN ENGLISH

If the error text mentions a structure problem…

…call it a validation error (a prompt bug).

Keep a list of "temporary glitch" signals.

If the error matches any of them…

…call it transient (it'll probably pass).

Anything else is a real, structural failure worth re-planning.

🔁
The infinite-loop guard

One special rule: if the Planner itself fails, never re-plan. Asking a broken GPS to recalculate forever is how agents get stuck. That single guard is what keeps the whole system from looping.

The fact-checker's veto

Remember the Critic from Module 2? When a specialist is marked "needs checking," a Critic is slotted in front of the next step. If the Critic says fail, a careful sequence kicks off:

1

Critic returns fail + a reason

→
2

The waiting child is marked skipped

→
3

A fresh Planner is spliced in with the failure reason

🎯
…but only once per branch (the cap)

That re-plan is allowed exactly one time per branch. If the redo also fails the Critic, the system stops trying and loudly warns you that the final answer is missing data — instead of silently looping or silently lying. Honesty over pretending, again.

Surviving a power-cord yank

Here's the scary one. What if the process is killed mid-run — laptop dies, someone hits Ctrl-C hard? The agent keeps an autosave. Every change to the board is written to disk safely:

CODE · persistence.py 
tmp = path.with_suffix(path.suffix + ".tmp")
tmp.write_text(data)
os.replace(tmp, path)
PLAIN ENGLISH

Write the new save to a temporary file first.

Fill it completely, off to the side.

Only then swap it into place in one instant move. If the plug is pulled mid-write, the old save is still intact. This is an atomic write.

Picking up where it left off

When you re-run with --resume, the agent loads the saved board and does one clever thing: any node that was mid-flight when the plug was pulled gets reset to "not started," so it runs again cleanly. Finished nodes are left untouched.

CODE · flow.py 
for _, d in graph.g.nodes(data=True):
    if d["status"] == "running":
        d["status"] = "pending"
PLAIN ENGLISH

Look at every node on the restored board.

If it was caught mid-run when we died…

…mark it "not started" so it runs fresh. Already-finished work is never redone — no wasted calls, no duplicates.

💾
Why you'd want this in your own apps

Long AI runs cost real money. Restarting from zero after a crash means paying twice. "Save progress safely, resume from the boundary" is a pattern worth asking your AI assistant to build into anything that runs for minutes.

06

Adding a Skill the Two-File Way

The whole architecture was built for this moment: teaching the agent a brand-new ability by touching exactly two text files — and zero lines of Python.

The metaphor: a standard wall outlet

Your home's wiring doesn't change when you buy a new lamp. As long as the plug fits the standard outlet, the lamp just works — the electrician never comes back. This agent is wired the same way. The "outlet" is a simple contract; any new specialist that fits it plugs right in.

🔌
The two-file rule

To add a skill: (1) add an entry to agent_config.yaml, (2) write a prompts/yourskill.md file. That's the entire job. The orchestrator (flow.py) is never edited.

Add a skill in two steps

1
Declare it in the config

A handful of YAML lines: its prompt file, which tools it may use, how creative it is.

2
Write its instructions

A Markdown file telling the AI what to do — ending with "reply as JSON." Done. It now shows up as a usable specialist.

Why does step 2 always say "reply as JSON"? Because that's the shape of the outlet. Every specialist returns JSON, so the orchestrator can handle all of them identically.

A chain that wires itself: Coder → Runner

The one ability the system ships ready to demo is the Coder: it writes Python, then a runner executes it. The cool part — nobody has to ask for the runner. The config glues them together:

CODE · agent_config.yaml 
coder:
  prompt: prompts/coder.md
  internal_successors: [sandbox_executor]
PLAIN ENGLISH

A specialist named "coder".

Its instructions live here.

"Whenever I finish, automatically add a code-runner after me." The Planner never has to know — the wiring is declared, not coded.

The contract between them

The Coder promises to emit exactly this shape, and the runner knows exactly where to look:

CODE · the Coder's output + skills.py 
# Coder returns:
{"code": "print(9_541_000)", "rationale": "..."}

# Runner picks it up:
code = r["output"].get("code") or code
out = run_python(code)
PLAIN ENGLISH

The Coder hands back a labelled package…

…with the Python in the "code" slot.

 

The runner reaches into the upstream package…

…grabs the "code" slot and runs it. If the slot is empty, it fails cleanly with "no code found."

A warning you should be able to call out

The runner executes code in a sandbox. But read what the code's own author says it is — and isn't:

⚠️
"Usability boundary, NOT a security boundary"

The sandbox stops a runaway loop from flooding your screen and scrubs secret keys from the environment. It does not stop malicious code from reading files or hitting the network. If an AI assistant ever tells you "it's sandboxed, so it's safe to run anything" — that's the kind of overclaim you now know to push back on.

CODE · sandbox.py 
scrubbed = {k: os.environ[k] for k in env_whitelist
            if k in os.environ}
PLAIN ENGLISH

Before running the code, build a clean, tiny set of environment values — only the safe ones on an allow-list (like the system PATH).

Your API keys are deliberately left out, so a script can't read and leak them.

Spot the anti-pattern

Suppose someone "adds" a Translator skill by editing the orchestrator like this. One line betrays that they missed the whole point of the design. Click it:

Which line breaks the two-file rule?

1for nid in ready:
2 skill = self.registry.get(skill_name)
3 if skill.name == "translator": do_translation_logic()
4 result = await run_skill(skill, nid, ...)
🚫
No special cases in the engine

A hardcoded if skill.name == "..." means the orchestrator now has to know about each skill. Do that a few times and the engine becomes a tangle of exceptions. The clean design treats every skill identically — special behavior lives in the prompt and config, never in the loop.

What you should never touch

The flip side of "easy to extend" is "know what's load-bearing." A few files are carried over from an earlier version and should be left alone:

perception.py · memory.py Carried over byte-for-byte from a prior session. Other parts quietly depend on them being unchanged.
gateway/ Treat it as a service you call, not code you patch. Found a real bug? File it; don't fix it inside your work.
🧠
The instinct to build

Knowing the boundary between "extend here" and "don't touch this" is exactly the judgment that lets you steer an AI assistant confidently through a codebase you didn't write.
